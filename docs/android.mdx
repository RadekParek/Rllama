---
title: Android
---

Ollama ships as a single Android APK containing the same Go server/CLI and the
same llama.cpp inference server as the desktop builds, compiled for
`arm64-v8a`. Nothing is downloaded after installation except model weights.

The APK is deliberately close to the desktop binary: there is no alternative
API, no mock server and no separate runtime installer. Installing it puts the
real `ollama` command on your phone, and `ollama serve` runs in the background
so the stock HTTP API answers on `127.0.0.1:11434`.

## Requirements

- Android 8.0 (API 26) or newer on an `arm64-v8a` device
- Roughly 2 GB of free RAM for small models, 8 GB or more for 7B models
- 2–5 GB of free storage per model

## Install

Download `rllama-ollama-<version>-android-arm64.apk` from the
`ollama-android-apk` artifact of the `android` workflow (or from the release
assets when a release was published) and install it. The APK is debug-signed, so
allow "install unknown apps" for your file manager or use `adb install`.

```shell
adb install -r rllama-ollama-<version>-android-arm64.apk
```

## Using the app

The app opens a console. The bundled `ollama` binary is on `PATH` inside it, and
the server starts automatically:

```shell
$ ollama list
$ ollama pull gemma3:1b
$ ollama run gemma3:1b "summarize this repo"
$ curl -s localhost:11434/api/tags
```

The long-press menu copies the transcript, the ↑/↓ keys recall previous
commands, and **Stop** interrupts the running command. The foreground service
keeps the server alive when you leave the app.

Ollama's defaults are untouched: models live in `$HOME/.ollama/models` inside
the app's private directory, and the API listens on `127.0.0.1:11434`. Because
the server binds the loopback interface only, other devices cannot reach it;
expose it with your own `OLLAMA_HOST` if you need that:

```shell
$ OLLAMA_HOST=0.0.0.0:11434 ollama serve
```

### Connecting Claude Code

`ollama serve` exposes the same `/api/*` and `/v1/*` routes (including
`/v1/messages`) as on the desktop, so a client that runs on the phone or through
a port forward can use the usual settings:

```
OLLAMA_HOST=http://127.0.0.1:11434
```

## What is in the APK

| Component | Path inside the APK |
| --- | --- |
| Ollama Go server + CLI | `lib/arm64-v8a/libollama.so` |
| llama.cpp inference server (CPU, static) | `lib/arm64-v8a/libllama-server.so` |
| Third-party license texts | `assets/licenses/` |
| App: console, foreground service, process host | `classes*.dex` |

Android only extracts APK entries named `lib*.so` into the executable native
library directory, which is why the two executables carry that name; they are
ordinary Ollama binaries otherwise.

The exact byte size of every entry is printed by the `Report APK contents` step
of the `android` workflow (`unzip -v` also shows it locally).

### Why the APK is much smaller than the Windows installer

The Windows and macOS distributions bundle one inference backend per GPU vendor
— CUDA (`cublas`, `cudart`), ROCm, Vulkan — plus several `llama-server` variants
and their runtime DLLs. Those thousands of megabytes are GPU-specific and
useless on a phone. The APK ships one ABI with the CPU backend only, statically
linked. Model weights are not bundled in either case: they are downloaded after
installation.

## Build

```shell
# native payload
ANDROID_NDK_HOME=/path/to/ndk ./scripts/build_android.sh -a arm64-v8a

# APK
cd android
gradle assembleDebug
# output: app/build/outputs/apk/debug/app-debug.apk
```

In CI this is `.github/workflows/android.yaml`, which runs on tags, on `main`
pushes that touch the app or native inputs, on pull requests, and manually via
*Run workflow*. It builds exactly one APK, verifies that both payload entries
are present and executable-on-install, and uploads `ollama-android-apk`. On a
`v*` tag it also attaches the APK to the existing GitHub release when one is
present.

### Signing

The APK is the standard debug build: installable anywhere with "install unknown
apps" enabled, and compatible with `adb install -r` upgrades. No keystore
secrets are needed. Sign it with your own key if you publish it through a store.

## Verified and unverified behaviour

Verified in CI on every build:

- both executables are built for `arm64-v8a` (`file` reports AArch64 ELF)
- the APK contains `lib/arm64-v8a/libollama.so` and
  `lib/arm64-v8a/libllama-server.so` as installer-extractable entries
- the packaged manifest declares the console activity as the launcher
- the app compiles against SDK 35

Not verified automatically — no physical device is attached to CI, so these are
manual steps:

- installing the APK on a phone, starting `ollama serve`, `ollama pull`, a real
  generation, and a check that inference still works with networking disabled

If you run those checks, report the results you actually see; do not assume
they passed.

## Limitations

- `arm64-v8a` only; no 32-bit ARM, no `x86_64` (except when built explicitly
  with `scripts/build_android.sh -a x86_64` and matching `abiFilters`).
- CPU inference only: no Vulkan/OpenCL backend and no GPU offload.
- The desktop chat window (`app/ui`, Windows/macOS only) is not included; the
  phone exposes the CLI and the HTTP API.
- No model auto-update, no tray icon, no desktop app updater.

## Troubleshooting

- **"native payload missing"** — the APK was built without running
  `scripts/build_android.sh` first, so `jniLibs/arm64-v8a` was empty.
- **Model load fails / the app is killed** — lower the context length
  (`OLLAMA_CONTEXT_LENGTH`), pull a smaller quantisation, and close other apps.
- **`ollama pull` fails with DNS/network errors** — the network may block the
  registry; try another network or import a GGUF file with `ollama create`.
- **`llama-server` not found by the server** — the copy lost its executable bit;
  rebuild the payload with `scripts/build_android.sh` (it applies `chmod 0755`).
